AI Harness Engineering 스캐폴딩 리팩터링 V3 프롬프트
=====================================================
원본 지시사항 + C1~C5 결정사항 통합본

목표:
문서 구조를 단순화하면서도, 프로젝트 경험이 원본 하네스로 되돌아가
다음 프로젝트의 에이전트 실행 능력을 개선하는 self-improving 구조를 만드는 것.

# 1. 최종 구조 방향

최종 구조는 아래 4개 축으로 정리합니다.

- core/ : 모든 프로젝트의 공통 원칙과 표준
- templates/ : 프로젝트 문서 뼈대와 선택형 Pack
- agent_runtime/ : 계속 self-improving 되는 에이전트 실행 커널
- knowledge/ : lessons, anti-patterns 등 축적 지식

최종 구조 기준:

ai_engineering_docs/
├── README.md
├── QUICKSTART.md
├── SELF_IMPROVING.md
├── core/
├── templates/
│   ├── base/
│   └── packs/
│       ├── web-saas/
│       ├── mobile-game/
│       ├── ai-agent-product/
│       └── data-tool/
├── agent_runtime/
│   ├── agents/
│   ├── commands/
│   ├── hooks/
│   ├── shared/
│   │   └── ESCALATION_BLOCK.md
│   ├── VERSION.md
│   ├── CHANGELOG.md
│   └── UPGRADE_GUIDE.md
└── knowledge/
    ├── LESSONS_LEARNED.md
    └── ANTI_PATTERNS.md

# 2. WORKFLOW.md 위치와 역할

WORKFLOW.md는 최종 프로젝트 루트에 둡니다.

최종 프로젝트 루트의 핵심 문서는 아래 5개입니다.

project/
├── CONSTITUTION.md
├── WORKFLOW.md
├── CLAUDE.md
├── AGENTS.md
└── QUALITY_SCORE.md

WORKFLOW.md는 사람-에이전트 협업 운영 계약서입니다.
운영 원칙만 간결하게 유지하고, 실제 실행 절차는 agent_runtime/commands/가 담당합니다.

core/에는 WORKFLOW_TEMPLATE.md를 둡니다.
templates/base/에는 실제 프로젝트에 복사될 WORKFLOW.md를 둡니다.

# 3. Pack 운영 방식

프로젝트는 Base only로 시작 가능해야 합니다.

기본 시작:
templates/base + agent_runtime

Pack은 초기부터 반드시 고르는 것이 아니라, 개발 중 필요할 때 추가 적용하는 선택형 확장 모듈입니다.

예:
- 인증/API/DB 보안이 필요해지면 web-saas Pack 추가
- LLM 요약/추천 기능이 들어가면 ai-agent-product Pack 추가
- 게임 성능/스테이지 검증이 필요하면 mobile-game Pack 추가
- ETL/리포팅/데이터 정합성이 필요하면 data-tool Pack 추가

Pack은 없애지 않습니다.
프로젝트에서 반복 가능한 규칙은 나중에 templates/packs/로 승격할 수 있어야 합니다.

# 4. Pack EXT merge 규칙

여러 Pack을 조합할 때는 additive merge를 기본으로 합니다.

- Base 문서를 먼저 둡니다.
- Pack의 EXT 내용은 Base 문서의 "Pack Extensions" 섹션에 누적 추가합니다.
- 각 항목에는 출처 Pack을 표시합니다.
- 단순 덮어쓰기나 마지막 Pack 우선 방식은 사용하지 않습니다.
- 충돌 시 보안, 개인정보, 데이터 무결성, 비용 폭주 방지, timeout, retry, coverage, 성능 수치 등은 더 엄격한 기준을 우선합니다.
- 둘 다 만족 가능하면 둘 다 유지합니다.
- 동시에 만족 불가능하거나 판단이 애매하면 docs/exec/open-decisions.md에 등록하고 사람에게 결정 요청합니다.

# 5. agent_runtime 원칙

기존 claude_code/는 agent_runtime/으로 변경합니다.

agent_runtime/은 유일한 upstream 실행 커널입니다.
templates/base/.claude/와 templates/packs/*/.claude/는 만들지 않습니다.

새 프로젝트 생성 시:
agent_runtime/ → project/.claude/ 로 복사됩니다.

Pack 전용 command가 필요해도 Pack 내부에 .claude를 만들지 않습니다.

예:
- 금지: templates/packs/web-saas/.claude/commands/check-rls.md
- 허용: agent_runtime/commands/check-rls.md

Pack은 기준과 체크리스트를 정의하고, 실행 command/agent/hook은 항상 agent_runtime/에 둡니다.

# 6. 프로젝트별 runtime 커스터마이징

project/.claude/는 local runtime이므로 프로젝트 특수성에 맞게 수정할 수 있습니다.

원칙:
- agent_runtime/은 upstream 원본입니다.
- project/.claude/는 복사된 local runtime입니다.
- local runtime 수정은 허용합니다.
- 좋은 개선이면 /learn으로 Backport Proposal을 생성합니다.
- Owner가 승인하면 agent_runtime/에 반영합니다.
- 승인하지 않으면 해당 프로젝트 내부 fork 상태로 유지합니다.
- local runtime 수정이 있으면 README.md, CLAUDE.md 또는 .harness/manifest.yml에 기록합니다.

# 7. agent_runtime 버전 관리

agent_runtime/에는 아래 3개 문서를 둡니다.
- VERSION.md
- CHANGELOG.md
- UPGRADE_GUIDE.md

버전 정책은 Semantic Versioning을 따릅니다.
- patch: 오타, 문구 개선, non-breaking check 추가
- minor: 새로운 command, hook, agent 규칙 추가
- major: 기존 command contract 변경, 필수 문서 구조 변경, 호환성 깨짐

기존 프로젝트의 runtime 업그레이드는 자동으로 하지 않습니다.
Owner 또는 사람이 UPGRADE_GUIDE.md를 보고 승인한 뒤 수동으로 진행합니다.

# 8. ESCALATION_PROTOCOL 처리

ESCALATION_PROTOCOL.md는 core 독립 문서로 유지하지 않습니다.

대신 runtime 내부 공통 블록으로 둡니다.
agent_runtime/shared/ESCALATION_BLOCK.md

이 파일은 모든 command와 agent가 공통으로 참조하는 에스컬레이션 형식입니다.
각 command와 agent는 자체 에스컬레이션 형식을 새로 만들지 말고,
agent_runtime/shared/ESCALATION_BLOCK.md를 참조해야 합니다.

WORKFLOW.md에는 에스컬레이션 원칙만 요약합니다.

# 9. knowledge 운영

knowledge/는 모든 프로젝트 lesson의 단순 합집합이 아닙니다.

프로젝트 lesson은 먼저 project/docs/exec/lessons.md에 기록합니다.
그 후 /learn을 통해 Backport Proposal을 만들고, Owner 승인 후에만 knowledge/, core/, templates/, agent_runtime/에 반영합니다.

판단 기준:
- 해당 프로젝트만 해당하면 project-local 유지
- 여러 프로젝트에 반복 가능하면 knowledge/LESSONS_LEARNED.md 승격 후보
- 반복 금지 패턴이면 knowledge/ANTI_PATTERNS.md 승격 후보
- 모든 프로젝트 공통 규칙이면 core/ 또는 agent_runtime/ 반영 후보
- 특정 유형 전용이면 templates/packs/[pack] 반영 후보

Owner 승인 전에는 원본을 직접 수정하지 않습니다.

# 10. SELF_IMPROVING.md 추가

self-improving 전체 실무 플로우는 README에 길게 넣지 말고 SELF_IMPROVING.md에 정리합니다.

README.md에는 개념 요약과 SELF_IMPROVING.md 링크만 둡니다.

SELF_IMPROVING.md에는 아래 내용을 포함합니다.
- 프로젝트 repo와 ai_engineering_docs 원본 repo의 역할 구분
- 새 프로젝트 생성 흐름
- project/.claude local runtime 수정 흐름
- docs/exec/lessons.md 기록 방식
- /learn 실행과 Backport Proposal 생성 방식
- Owner 승인 기준
- ai_engineering_docs 원본 repo에서 반영하는 방식
- VERSION.md, CHANGELOG.md, UPGRADE_GUIDE.md 업데이트 방식
- 다음 프로젝트에 최신 agent_runtime이 반영되는 흐름
- 기존 프로젝트는 자동 업그레이드하지 않고 수동 업그레이드한다는 원칙

# 11. .harness/manifest.yml 추가

templates/base/에 아래 파일을 추가합니다.
templates/base/.harness/manifest.yml

역할:
- 어떤 하네스 버전에서 시작했는지 기록
- 어떤 Pack이 적용되었는지 기록
- local runtime 수정 여부 기록
- runtime upgrade와 backport 판단에 사용

초기 예시:
harness_repo: ai_engineering_docs
agent_runtime_version: v0.0.0
base_template_version: v0.0.0
applied_packs: []
local_runtime_modified: false
runtime_customizations: []
backport_status: none

Pack을 나중에 추가하면 applied_packs에 적용 시점과 이유를 기록합니다.

# 12. 기존 문서 처리 기준

- AGENTS_PATTERN.md는 AGENT_SCHEMA.md로 변경합니다.
- ESCALATION_PROTOCOL.md는 독립 문서로 유지하지 않고 WORKFLOW.md 요약 + agent_runtime/shared/ESCALATION_BLOCK.md로 흡수합니다.
- GLOSSARY_TEMPLATE.md는 필수 문서가 아니라 선택 문서로 강등합니다.
- LESSONS_LEARNED.md와 ANTI_PATTERNS.md는 knowledge/로 이동합니다.
- PROJECT-SETUP-GUIDE.md와 PROJECT-DECISION-AND-PROMPTS.md는 QUICKSTART.md로 통합/축소합니다.
- templates_docs/saas와 templates_docs/game의 공통 내용은 templates/base 또는 agent_runtime으로 옮기고, 도메인 특화 내용은 templates/packs/로 재분류합니다.

# C1~C5 결정사항 (확정)

C1. Pack 파일 구조: V2 기준 유지
각 Pack은 README.md, QUALITY_EXT.md, ARCHITECTURE_EXT.md, AGENTS_EXT.md, CHECKLIST_EXT.md 5개 파일을 기본 구조로 가집니다.

C2. 보조 템플릿 처리:
- BACKPORT_PROPOSAL_TEMPLATE.md → core/ 유지
- README_TEMPLATE.md → templates/base/README.md 흡수
- open-decisions-template.md → templates/base/docs/exec/open-decisions.md
- tech-debt-template.md → templates/base/docs/exec/tech-debt.md
- GLOSSARY_TEMPLATE.md → templates/base/docs/optional/GLOSSARY.md (선택 문서)

C3. Pack EXT merge 방식: 옵션 B
Pack 적용 시 프로젝트 AGENTS.md, QUALITY_SCORE.md, ARCHITECTURE.md 등에
Pack Extensions 섹션으로 병합하고, orchestrate는 프로젝트 문서만 읽도록 합니다.

C4. Pack 적용 자동화: MVP는 수동(옵션 B), 장기적으로 /add-pack 커맨드(옵션 A)
초기에는 사람이 수동으로 Pack을 적용하되,
이후 agent_runtime/commands/add-pack.md를 추가해 manifest 업데이트와 EXT merge를 자동화합니다.

C5. core/templates 이중 구조 유지
core/*_TEMPLATE.md = 작성 표준/메타 가이드
templates/base/* = 실제 프로젝트에 복사되는 실행 양식
단, core는 원칙 중심, base는 복사 가능한 최소 양식으로 간결하게 유지합니다.
